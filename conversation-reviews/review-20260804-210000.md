## 问题列表

1. **SQLAlchemy 中 `db.add()` 的作用是什么？为什么修改密码时要用它？**
   > 原问题：这里为什么要这样做（指向 `db.add(user)`）

   关键点：
   - `db.add()` 不只是"添加新记录"，它的语义是"把这个对象纳入 Session 管理"
   - 新对象 → INSERT（Pending 状态），已有对象 → 追踪变更（UPDATE）
   - 对象处于 Detached（游离）状态时，需要 `db.add()` 重新关联到 Session

2. **为什么 SQLAlchemy 可能不知道对象被修改了？**
   > 原问题：不是有 user.password = hashed_new_pwd 就会跟踪这是一个被修改了的对象吗

   关键点：
   - 对象在当前活跃 Session 的 Identity Map 中时，SQLAlchemy **会**自动追踪
   - 只有对象处于 Detached（游离）状态时才不会自动追踪
   - `db.add()` 是防御性写法，确保对象在 Session 追踪范围内

3. **为什么注释掉 `db.add()` 也能正常更新？**
   > 原问题：我这里的 add 注释掉了也能正常更新，但是我的 user 来源是依赖项

   关键点：
   - FastAPI 的依赖缓存机制：同一请求中 `Depends(get_db)` 只调用一次
   - `get_current_user` 和 router 共享同一个 Session 实例
   - `user` 始终在同一 Session 的 Identity Map 中，修改自动追踪

4. **SQLAlchemy 怎么做事务管理？**
   > 原问题：SQLAlchemy怎么做事务管理

   关键点：
   - Session 就是事务容器，`commit()` 提交、`rollback()` 回滚
   - `flush()`：发送 SQL 到数据库但不提交（可获取自增 ID）
   - `refresh(obj)`：从数据库重新加载对象
   - `expire_on_commit=False`：commit 后对象属性保持原值，不触发重新查询

5. **Expired（过期）和 Detached（游离）有什么区别？**
   > 原问题：expire_on_commit 只是确保 commit 后对象是否可以使用吗

   关键点：
   - **Expired**：仍在 Session 的 Identity Map 中，访问属性时自动重新查库
   - **Detached**：不在 Session 中，访问属性直接报错 `DetachedInstanceError`
   - `expire_on_commit` 只影响 Expired 状态，不会导致 Detached

6. **什么情况下对象会变成游离态（Detached）？**
   > 原问题：那什么情况下，对象才会处于游离态

   关键点：
   - `session.close()`：Session 关闭，所有对象变游离
   - `session.expunge(obj)`：显式移除单个对象
   - Session 作用域结束（如 `async with` 退出）
   - 对象序列化/反序列化（pickle）

7. **FastAPI 中多个依赖项的执行顺序是什么？**
   > 原问题：这里有多个依赖项，执行顺序是什么

   关键点：
   - 从左到右，深度优先
   - 相同依赖（如 `get_db`）只执行一次，结果缓存共享
   - 执行顺序：解析请求体 → 解析 Header → 创建 Session → 调用认证函数 → 执行路由

8. **`get_db` 的 `finally` 什么时候执行？**
   > 原问题：get_current_user 执行完后，不是会进入依赖项 get_db 的 finally 吗

   关键点：
   - `yield` 依赖的 cleanup（commit/rollback/finally）在**整个请求结束后**才执行
   - 不是 `get_current_user` 返回时执行，而是 router 返回响应后才执行
   - 这保证了整个请求生命周期内 Session 都可用

9. **MissingGreenlet 错误是什么原因？**
   > 原问题：get_db e================ (sqlalchemy.exc.MissingGreenlet) greenlet_spawn has not been called

   关键点：
   - 在异步上下文中触发了同步的数据库查询（通常是懒加载关联属性）
   - 访问未加载的 `relationship` 属性时，SQLAlchemy 尝试同步懒加载，但异步模式不允许
   - 解决方案：查询时使用 `selectinload()` 或 `joinedload()` 预加载关联

10. **列表推导式中的元组解构是什么意思？**
    > 原问题：这个 rows 是一个元组列表，这里相当于是在推导式里解构元组吗

    关键点：
    - `for news, favorite_time, favorite_id in rows` 就是元组解构
    - 等价于 `for row in rows: news, favorite_time, favorite_id = row`
    - Python 支持 `a, b, c = (1, 2, 3)` 和 `first, *rest = (1, 2, 3, 4)` 语法

11. **如何实现旁路缓存（Cache-Aside）装饰器？**
    > 原问题：我要在这里实现一个缓存的装饰器，来修饰 get_categories，实现旁路缓存

    关键点：
    - Cache-Aside 模式：先查缓存 → 命中返回 → 未命中查库 → 写入缓存 → 返回
    - `@wraps(func)` 保留原函数元信息（`__name__`、`__doc__` 等）
    - 类装饰器通过 `__call__` 方法实现，返回 async wrapper

12. **类装饰器的 `__call__` 如何支持 `await`？**
    > 原问题：我这里要使用 await，我的 __call__ 方案应该怎么做

    关键点：
    - `__call__` 本身是同步的，但它返回一个 `async def wrapper` 函数
    - `__call__` 只是"制造"装饰器，`wrapper` 才是"执行"装饰逻辑的地方
    - 使用 `asyncio.iscoroutinefunction(func)` 检测函数类型，返回不同的 wrapper

13. **ORM 对象为什么无法 JSON 序列化？**
    > 原问题：在设置缓存时为什么报：Object of type Category is not JSON serializable

    关键点：
    - SQLAlchemy ORM 对象不是普通 dict，`json.dumps` 无法处理
    - 解决方案：使用 `fastapi.encoders.jsonable_encoder` 转换为 dict
    - `jsonable_encoder` 是 FastAPI 的"万能序列化器"，能处理 ORM、Pydantic、datetime 等

14. **为什么 Java 可以直接序列化对象而 Python 不行？**
    > 原问题：为什么 java 里面的类就可以直接序列化

    关键点：
    - Java 的 Jackson/Gson 通过反射机制自动读取字段和 getter
    - Python 的 `json` 模块故意只处理基本类型（dict、list、str、int 等）
    - Python 需要 `jsonable_encoder`、`Pydantic` 等工具来弥补

15. **`model_validate` 是干嘛的？**
    > 原问题：model_validate 是干嘛的

    关键点：
    - Pydantic v2 的方法，从 dict、ORM 对象、JSON 字符串等数据源验证并创建模型实例
    - 类似 Java 的 Jackson 从 JSON 反序列化为对象
    - 配合 `model_dump()` 可以实现 ORM → Pydantic → dict 的转换

16. **如何让缓存 key 支持动态拼接函数参数？**
    > 原问题：我想要在 key 由能够拼接修饰函数参数的能力，怎么做

    关键点：
    - key 支持三种形式：静态字符串、字符串模板（`"key:{offset}:{limit}"`）、函数
    - 使用 `Union[str, Callable[..., str]]` 类型注解
    - `Callable[..., str]` 表示"任意参数，返回 str 的函数"
